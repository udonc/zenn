手書きで `fetch()` を書くのは、URLの組み立て、レスポンスの型付け、ステータスコードごとのエラー処理…と考えることが多くて少々面倒ですよね。OpenAPIスキーマがあるなら、そこから型やコードを自動生成するツールに任せたくなります。

ただ、生成されたコードが、自分のプロジェクトに最適とは限りません。この記事ではKubbとneverthrowを組み合わせて、結果を `ResultAsync` で表現するfetchクライアントを作りながら、自分のプロジェクトにとっての理想のfetchクライアントを設計する考え方を整理します。

## 環境

- Node.js v24.19.0
- pnpm v11.25.0
- TypeScript v7.0.2
- Kubb v5.0.6
- neverthrow v8.2.0

## Kubbを使ってみる

[Kubb](https://kubb.dev/)はコード生成のためのメタフレームワークです。様々なプラグインを組み合わせてOpenAPIスキーマからTypeScriptの型やクライアント、React Queryのhooksなどのコードを生成できます。

### インストール

npmパッケージとしてインストールします。

```bash
pnpm i -D kubb
```

今回必要なプラグインも併せてインストールします。

```bash
pnpm i -D @kubb/plugin-ts @kubb/plugin-fetch
```

`@kubb/plugin-ts` はTypeScriptの型を、 `@kubb/plugin-fetch` はfetchクライアントを生成するプラグインです。

### 設定ファイルとOpenAPIスキーマの追加

コードを生成するにはKubbの設定ファイル( `kubb.config.ts` )と元になるOpenAPIスキーマの追加が必要です。

```ts:kubb.config.ts
import { pluginFetch } from "@kubb/plugin-fetch";
import { pluginTs } from "@kubb/plugin-ts";
import { defineConfig } from "kubb";

export default defineConfig({
  input: "./openapi.yaml", // 生成元になるOpenAPIスキーマ
  output: {
    path: "./generated", // 生成したコードをどこに出力するか
    clean: true, // 生成のたびに `./generated` ディレクトリを削除する設定
  },
  plugins: [
    pluginTs(),
    pluginFetch({
      baseURL: "https://api.example.com/v1",
    }),
  ],
});
```

元になるOpenAPIスキーマも追加しておきます。
`GET /books/{isbn}` という1つのエンドポイントが `200 | 404` を返すだけのシンプルな例を使います。

### OpenAPIから生成してみる

以下のコマンドでコード生成が実行され、先ほど設定したパスに出力されます。

```bash
pnpm kubb generate
```

実行すると型やクライアント用の共通コードなどを含めた複数のファイルが生成されました。
実際にAPIから本の情報を取得するための `getBook()` 関数が追加されています。

```ts:generated/clients/getBook.ts
/**
* Generated by Kubb (https://kubb.dev/).
* Do not edit manually.
*/

import type { Options, Unwrappable, RequestResult } from '../.kubb/client'
import type { GetBookOptions, GetBookResponses } from '../types/GetBook'
import { client, withUnwrap } from '../.kubb/client'

/**
 * @summary 書籍を 1 件取得する
 * {@link /books/:isbn}
 */
export function getBook<ThrowOnError extends boolean = true>(options: Options<GetBookOptions, ThrowOnError>): Unwrappable<RequestResult<GetBookResponses, ThrowOnError>> {
  const { client: request = client, ...config } = options

  return withUnwrap(request({ method: 'GET', url: '/books/{isbn}', ...config }) as Promise<RequestResult<GetBookResponses, ThrowOnError>>)
}
```

呼び出し側のイメージは以下のようになります。

```ts:index.ts
import { getBook } from "./generated/clients";
import type { ApiError } from "./generated/types/ApiError";
import type { Book } from "./generated/types/Book";

try {
  const result = await getBook({
    path: { isbn: "4299039009" },
    throwOnError: false,
  });

  switch (result.status) {
    case 200:
      result.data satisfies Book; // 型が Book に絞られている
      break;
    case 404:
      result.error satisfies ApiError;
      break;
    default:
      result satisfies never;
  }
} catch (e) {
  console.error("transport error", e);
}
```

生成された `getBook()` 関数の引数としてパスパラメータの `isbn: string` を型安全に渡すことができます。
また、 `throwOnError: false` を渡すことで、エラーレスポンスの発生時にthrowせず `result.status` で判別できるユニオン型として受け取れるインターフェースで使用できます。

## 便利だけど理想ではない

これだけでも十分便利ですが、個人的には不満が残ります。 `throwOnError: false` は、返ってきたレスポンスのステータスコードが2xx系以外だった場合にthrowしないという挙動です。ただ、そもそもリクエストが送信できない場合やレスポンスが正しくパースできない場合はthrowされてしまうので、呼び出し側では引き続き `try...catch` によるハンドリングが必要です。

## 呼び出し側でneverthrowを使ってみる

[neverthrow](https://github.com/supermacro/neverthrow)はエラーハンドリングのためのライブラリです。例外をthrowする代わりに値で返すことによって型安全にエラーハンドリングができるようになります。

### インストール

```bash
pnpm i neverthrow
```

呼び出し側を修正してneverthrowを使ったパターンにしてみます。

```ts:index.ts
import { err, ok, type Result, ResultAsync } from "neverthrow";
import { getBook } from "./generated/clients";
import type { ApiError } from "./generated/types/ApiError";
import type { Book } from "./generated/types/Book";

type GetBookError =
  | { kind: "notFound"; cause: ApiError }
  | { kind: "transport"; cause: unknown }
  | { kind: "unexpected"; cause: unknown };

const fetchBook = (isbn: string): ResultAsync<Book, GetBookError> =>
  ResultAsync.fromPromise(
    getBook({ path: { isbn }, throwOnError: false }),
    (cause): GetBookError => ({ kind: "transport", cause }),
  ).andThen((res): Result<Book, GetBookError> => {
    switch (res.status) {
      case 200:
        return ok(res.data);
      case 404:
        return err({ kind: "notFound", cause: res.error });
      default:
        return err({ kind: "unexpected", cause: res satisfies never });
    }
  });

const result = await fetchBook("4299039009");

result.match(
  (book) => console.log("ok", book.title),
  ({ kind, cause }) => console.error(kind, cause),
);
```

`ResultAsync.fromPromise()` を使用することでthrowableな処理をResultAsync型に包むことができます。先ほどは `catch` が必要だったネットワークエラー等は `GetBookError` に包まれて返却されるので、呼び出し側で `try...catch` を使用する必要がなくなりました。

## 安全になったけどボイラープレートが増えた

呼び出し側で `try...catch` を使わずに型安全にエラーハンドリングができるようになりました。`fetchBook()` の中身を見返してみると、やっていることは次の3つだけです。

- `GetBookError` のようなエラー型の定義
- `ResultAsync.fromPromise()` で `getBook()` を包む処理
- `switch (res.status)` でレスポンスを `ok` / `err` に振り分ける処理

エンドポイントが増えれば、この3つをその数だけ手で書くことになりますが、どのステータスコードがどの型を返すかはOpenAPIスキーマにすでに書かれているので、3つとも機械的に導けるものです。人間が考えて書く部分はほとんどありません。

## Kubbに生成させる

Kubbのプラグインを自作することで生成するコードをより細かくカスタマイズできます。呼び出し側のボイラープレートを自作プラグイン側で生成することで、人の手でわざわざ書くといったことを避けられそうです。

### どういうコードを生成させるか考える

実際にプラグインの実装に入る前に、どういうコードを生成させたいのかを整理しておくとよさそうです。 `getBook()` の理想の形を考えてみましょう。

```ts:理想の getBook.ts のイメージ
import { err, ok, type Result, ResultAsync } from "neverthrow";
import {
  type CallResult,
  client,
  type DataOf,
  type DataShape,
  type Options as KubbOptions,
  type SuccessOf,
  type SuccessStatusCode,
  type ToStatusNumber,
} from "./generated/.kubb/client";
import type { Book } from "./generated/types/Book";
import type {
  GetBookOptions,
  GetBookResponses,
} from "./generated/types/GetBook";

// --- 共通化できる部分 ---

/** レスポンスの取得に失敗（接続失敗, abort, body のパース失敗など） */
export type TransportError = { kind: "transport"; cause: unknown };

/** 想定されたエラーレスポンス */
export type HttpError<TResponses> = {
  [S in ErrorStatusOf<TResponses>]: {
    kind: "http";
    status: ToStatusNumber<S>;
    body: DataOf<TResponses[S]>;
  };
}[ErrorStatusOf<TResponses>];

/** 想定されていないレスポンス */
export type UnexpectedResponseError = {
  kind: "unexpected";
  status: number;
  body: unknown;
};

export type RequestError<TResponses> =
  | TransportError
  | HttpError<TResponses>
  | UnexpectedResponseError;

/** 生成した関数が受け取る options */
export type Options<TData extends DataShape> = Omit<
  KubbOptions<TData, false>,
  "throwOnError" // `throwOnError = false` で固定するので Omit している
>;

type ErrorStatusOf<TResponses> = Exclude<keyof TResponses, SuccessStatusCode>;
type SuccessDataOf<TResponses> = DataOf<SuccessOf<TResponses>>;

const isSuccessStatus = (status: number): boolean =>
  status >= 200 && status < 300;

const isDocumented = (
  documented: ReadonlyArray<number>,
  status: number,
): boolean => documented.includes(status);

/** Kubb client の実行を `ResultAsync` で包む */
export const toResultAsync = <TResponses>(
  /** Kubb client の結果 */
  call: Promise<CallResult>,
  /** OpenAPI に定義されたレスポンスの status のリスト */
  documented: ReadonlyArray<ToStatusNumber<keyof TResponses>>,
): ResultAsync<SuccessDataOf<TResponses>, RequestError<TResponses>> =>
  ResultAsync.fromPromise(
    call,
    (cause): RequestError<TResponses> => ({ kind: "transport", cause }),
  ).andThen(
    (res): Result<SuccessDataOf<TResponses>, RequestError<TResponses>> => {
      const success = isSuccessStatus(res.status);
      if (!isDocumented(documented, res.status)) {
        return err({
          kind: "unexpected",
          status: res.status,
          body: success ? res.data : res.error,
        });
      }
      // `if(isDocumented)` の early return を通過したので `TResponses` として読み替えてOK
      return success
        ? ok(res.data as SuccessDataOf<TResponses>)
        : err({
            kind: "http",
            status: res.status,
            body: res.error,
          } as HttpError<TResponses>);
    },
  );

// --- エンドポイントごとに生成する部分 ---

export type GetBookError = RequestError<GetBookResponses>;

/**
 * @summary 書籍を 1 件取得する
 * {@link /books/:isbn}
 */
export function getBook(
  options: Options<GetBookOptions>,
): ResultAsync<Book, GetBookError> {
  const { client: request = client, ...config } = options;

  return toResultAsync<GetBookResponses>(
    request({
      ...config,
      method: "GET",
      url: "/books/{isbn}",
      throwOnError: false,
    }),
    [200, 404],
  );
}
```

イメージを掴むために1つのファイルにまとめましたが、実装ではコメントで区切った2つの部分を別ファイルに分けます。前半の型や `toResultAsync()` はエンドポイントが増えても変わらないので1回用意すれば済み、Kubbに生成させるのは後半だけです。

やっていることは前のセクションで挙げた3つと同じで、エラー型の定義、`ResultAsync` で包む処理、レスポンスを `ok` / `err` に振り分ける処理です。ただし後ろの2つはどのエンドポイントでも手順が同じなので `toResultAsync()` に汎用化でき、エンドポイントごとに違うのはエラー型と、OpenAPIに書かれたステータスコードの一覧 `[200, 404]` だけになりました。型は実行時に消えてしまうので、この一覧だけは値として生成側から渡す必要があります。

共通部分は少々込み入っていますが、呼び出し側は以下のようにシンプルになります。

```ts:index.ts
import { getBook } from "./getBook";

const result = await getBook({ path: { isbn: "4299039009" } });

result.match(
  (book) => console.log("ok", book.title),
  (e) => {
    switch (e.kind) {
      case "http":
        console.error(e.status, e.body.message); // status は 404 に絞られる
        break;
      case "transport":
        console.error("transport", e.cause);
        break;
      case "unexpected":
        console.error("unexpected", e.status, e.body);
        break;
      default:
        e satisfies never;
    }
  },
);
```

### まずは小さなプラグインから

先ほど整理したコードをいきなり全て生成するのは大変なので、まずは「エンドポイントごとに1つファイルを吐く」だけの小さなプラグインを作って、Kubbのプラグインがどう動くのかを見ていきます。

Kubbのプラグインは `kubb/kit` から提供される `definePlugin()` で定義します。ここでは `getBook` のメソッドとパスを文字列として出力するだけの `pluginHello` を作ってみます。ファイル名が `plugin-fetch-neverthrow.ts` なのは、このプラグインを段階的に作り変えて最終的なプラグインにするためです。

コードを処理の流れに沿って3つに分けて見ていきます。

#### プラグインを定義する

プラグインは `definePlugin()` に関数を渡して定義します。関数は `kubb.config.ts` でユーザーが渡したオプションを受け取り、プラグイン名と `hooks` を返します。Kubbはビルドの各時点で `hooks` を呼び出しますが、今回使うのは最初に1回だけ呼ばれる `kubb:plugin:setup` です。ここでやることは2つで、`setOptions()` で既定値を埋めたオプションを確定させ、`addGenerator()` でジェネレータを登録します。

```ts:kubb-plugins/plugin-fetch-neverthrow.ts（抜粋）
export const pluginHello = definePlugin<PluginHello>((options) => {
  // ユーザーが省略した項目に既定値を埋める
  const { output = { path: "hello", barrel: { type: "named" } } } = options;
  return {
    name: "plugin-hello",
    options,
    hooks: {
      // ビルド開始時に1回だけ呼ばれる
      "kubb:plugin:setup"(ctx) {
        // 既定値を埋めたオプションを確定させる。ジェネレータ側では ctx.options になる
        ctx.setOptions({ output });
        // ファイルを組み立てるジェネレータを登録する
        ctx.addGenerator(helloGenerator);
      },
    },
  };
});
```

#### ジェネレータでファイルを返す

ジェネレータは `defineGenerator()` で定義します。`operation()` はOpenAPIの操作ごとに1回ずつ呼ばれ、引数の `node` から `operationId` や `method`、`path` が取れます。返り値はファイルの配列で、`ctx.resolver.file()` で出力先を決め、`ast.factory` で中身を組み立てます。返したファイルはKubbが書き出してくれます。

```ts:kubb-plugins/plugin-fetch-neverthrow.ts（抜粋）
const helloGenerator = defineGenerator<PluginHello>({
  name: "hello-generator",
  // OpenAPI のオペレーションごとに1回ずつ呼ばれる
  operation: (node, ctx) => {
    // 出力先のファイル名とパスを決める。output の設定はここで反映される
    const file = ctx.resolver.file({
      name: node.operationId,
      extname: ".ts",
      root: ctx.root,
      output: ctx.options.output,
    });
    return [
      // 1ファイル = createFile。中身は createSource の nodes に並べる
      ast.factory.createFile({
        baseName: file.baseName,
        path: file.path,
        sources: [
          ast.factory.createSource({
            name: node.operationId,
            isExportable: true,
            isIndexable: true, // index.ts にまとめて export する対象にする
            nodes: [
              // 今はただの文字列。ここを先ほどのコードに作り変えていく
              ast.factory.createText(
                `export const ${node.operationId} = "${node.method} ${node.path}";\n`,
              ),
            ],
          }),
        ],
      }),
    ];
  },
});
```

#### オプションの型をつなぐ

最後に、ファイルの先頭で定義している型です。ユーザーから受け取る形が `Options`、`setOptions()` で確定した後の形が `ResolvedOptions` で、`PluginHello` がこの2つとプラグイン名を束ねます。これを `definePlugin()` と `defineGenerator()` の両方に渡しておくことで、ジェネレータ側の `ctx.options.output` に型がつきます。

```ts:kubb-plugins/plugin-fetch-neverthrow.ts（抜粋）
// ユーザーが kubb.config.ts で渡すオプション。省略できる
type Options = {
  output?: Output;
};

// setOptions() で確定した後のオプション。ジェネレータの ctx.options はこの型になる
type ResolvedOptions = {
  output: Output;
};

// プラグイン名と2つのオプション型をまとめる。definePlugin と defineGenerator の両方に渡す
type PluginHello = PluginFactoryOptions<
  "plugin-hello",
  Options,
  ResolvedOptions
>;
```

:::details 全体のコード
```ts:kubb-plugins/plugin-fetch-neverthrow.ts
import type { Output, PluginFactoryOptions } from "kubb/kit";
import { ast, defineGenerator, definePlugin } from "kubb/kit";

type Options = {
  output?: Output;
};

type ResolvedOptions = {
  output: Output;
};

type PluginHello = PluginFactoryOptions<
  "plugin-hello",
  Options,
  ResolvedOptions
>;

const helloGenerator = defineGenerator<PluginHello>({
  name: "hello-generator",
  operation: (node, ctx) => {
    const file = ctx.resolver.file({
      name: node.operationId,
      extname: ".ts",
      root: ctx.root,
      output: ctx.options.output,
    });
    return [
      ast.factory.createFile({
        baseName: file.baseName,
        path: file.path,
        sources: [
          ast.factory.createSource({
            name: node.operationId,
            isExportable: true,
            isIndexable: true,
            nodes: [
              ast.factory.createText(
                `export const ${node.operationId} = "${node.method} ${node.path}";\n`,
              ),
            ],
          }),
        ],
      }),
    ];
  },
});

export const pluginHello = definePlugin<PluginHello>((options) => {
  const { output = { path: "hello", barrel: { type: "named" } } } = options;
  return {
    name: "plugin-hello",
    options,
    hooks: {
      "kubb:plugin:setup"(ctx) {
        ctx.setOptions({ output });
        ctx.addGenerator(helloGenerator);
      },
    },
  };
});
```
:::


`generated/hello/` に、操作ごとのファイルと、それをまとめる `index.ts` が出力されました。`index.ts` は `isIndexable: true` を付けたソースをまとめたものです。

```ts:generated/hello/getBook.ts
export const getBook = "GET /books/{isbn}";
```

```ts:generated/hello/index.ts
export { getBook } from './getBook'
```

中身はまだただの文字列ですが、「OpenAPIの操作を1つ受け取って、ファイルを1つ返す」という流れはこれで揃いました。あとは `createText()` に渡す文字列を先ほど整理したコードに近づけていくだけです。

### ここから先はClaude Codeに任せちゃおう

`pluginHello` までは手で書いてきましたが、自分が怠惰な人間であることを思い出しました。ここから先のプラグイン本体とテストはClaude Code（モデルはFable 5.1）に任せます。渡したのは3つです。「[自分で整理したコード](#どういうコードを生成させるか考える)」を `getBook.dummy.ts` として保存したもの、先に作った `pluginHello`、そして「生成物が `getBook.dummy.ts` の後半と一致し、`tsc --noEmit` を通ること」という受け入れ条件です。あわせて、プラグイン名は `plugin-fetch-neverthrow`、出力先は `fetch-neverthrow/` に改めるよう伝えています。

自分がやったのは主に、テストのアウトラインの確認と、返ってきた生成物を目標と見比べることです。この節では、コードの中身を1行ずつ追うのではなく、何を渡して何を確かめたかと、自分で決めたことを書きます。

#### テストで受け入れ条件を固定する

実装はTDDで進めてもらいました。テストのコードは細部まで追わず、`describe` と `it` の見出しで何を検証しているかを重点的に確認しました。

```
pluginFetchNeverthrow
  共通部（.kubb/neverthrow.ts）
    Kubb client の型を隣の client.ts から import する
    toResultAsync と Result 型群を export する
  operation ごとの生成物（fetch-neverthrow/getBook.ts）
    必要な import が揃っている
    operation 固有の Error 型を export する
    dummy と同じ形の関数を生成する
    barrel（index.ts）から getBook を export する
  生成物の型
    tsc --noEmit を通り、呼び出し側で期待する型に絞られる
```

「dummy と同じ形の関数を生成する」が受け入れ条件の中心です。生成された `getBook.ts` に、`getBook.dummy.ts` の後半と同じ関数がそのまま含まれていることを文字列の比較で固定しています。


#### 工夫した点

任せた中で、自分の判断で決めたことは2つあります。

##### 目標のコードをそのままテストの期待値にした

「[自分で整理したコード](#どういうコードを生成させるか考える)」の後半を、テストの `expected` として文字どおり使ってもらいました。先ほどのコードがそのまま受け入れ条件になるので、設計を変えたいときは目標のコードを直せばテストがfailしてくれます。

##### テンプレートの拡張子を `.ts.txt` にした

共通ファイルのテンプレートを用意して、生成時に `.kubb/` の中にコピーする機能があるのですが、テンプレートはコピー先の隣にある `client.ts` をimportするので、コピー前の位置ではそのパスが解決できません。`.ts` のままだと型チェックとエディタの診断が赤くなります。

最初、Claude CodeはLinter (Biome) やtsconfigの `exclude` で解決しようとしていました。でも、ファイル1つのためにグローバルな設定を足すよりは、拡張子を変えてTypeScriptとして扱わせないほうがエレガントだと思ったので、そちらにしました。私の勝ちです。

```ts:kubb-plugins/plugin-fetch-neverthrow.ts（抜粋）
/** 共通ランタイムを `.kubb/` に配置するファイルノードを作る */
const createRuntimeFile = (root: string): ast.UserFileNode => ({
  baseName: RUNTIME_BASENAME,
  path: resolveRuntimePaths(root).neverthrow,
  // plugin-fetch と同じくテンプレートをそのままコピーする。出力先で隣の client.ts を import する都合上、
  // コピー元のファイルの拡張子を .ts.txt にして型チェックとエディタの診断から外している
  copy: fileURLToPath(
    new URL("./templates/neverthrow.ts.txt", import.meta.url),
  ),
});
```

プラグイン全体のコードは次のとおりです。

:::details 全体のコード
```ts:kubb-plugins/plugin-fetch-neverthrow.ts
import path from "node:path";
import { fileURLToPath } from "node:url";
import { pluginFetchName } from "@kubb/plugin-fetch";
import type { ResolverTs } from "@kubb/plugin-ts";
import { pluginTsName } from "@kubb/plugin-ts";
import type { Group, Output, PluginFactoryOptions } from "kubb/kit";
import { ast, defineGenerator, definePlugin, Url } from "kubb/kit";

type Options = {
  /**
   * @default { path: "fetch-neverthrow", barrel: { type: "named" } }
   */
  output?: Output;
};

type ResolvedOptions = {
  output: Output;
};

export type PluginFetchNeverthrow = PluginFactoryOptions<
  "plugin-fetch-neverthrow",
  Options,
  ResolvedOptions
>;

export const pluginFetchNeverthrowName =
  "plugin-fetch-neverthrow" satisfies PluginFetchNeverthrow["name"];

// --- 共通ランタイム（`.kubb/neverthrow.ts`） ---

/** 共通ランタイムのファイル名 */
const RUNTIME_BASENAME = "neverthrow.ts";

/** 出力ルート配下の `.kubb/` にあるランタイムファイルの絶対パスを解決する。 */
const resolveRuntimePaths = (root: string) => ({
  client: path.resolve(root, ".kubb/client.ts"),
  // plugin-fetch が作成する `client.ts` と同じ位置に neverthrow のランタイムを配置する
  neverthrow: path.resolve(root, ".kubb", RUNTIME_BASENAME),
});

/** 共通ランタイムを `.kubb/` に配置するファイルノードを作る */
const createRuntimeFile = (root: string): ast.UserFileNode => ({
  baseName: RUNTIME_BASENAME,
  path: resolveRuntimePaths(root).neverthrow,
  // plugin-fetch と同じくテンプレートをそのままコピーする。出力先で隣の client.ts を import する都合上、
  // コピー元のファイルの拡張子を .ts.txt にして型チェックとエディタの診断から外している
  copy: fileURLToPath(
    new URL("./templates/neverthrow.ts.txt", import.meta.url),
  ),
});

// --- operation ごとの生成 ---

type OperationNames = {
  /** 生成する関数名（例: getBook） */
  fn: string;
  /** plugin-ts が生成する options 型（例: GetBookOptions） */
  options: string;
  /** plugin-ts が生成する responses 型（例: GetBookResponses） */
  responses: string;
  /** この plugin が生成する error 型（例: GetBookError） */
  error: string;
};

type SuccessType = {
  /** 成功時のデータ型の式（例: Book） */
  expression: string;
  /** 式が参照する型の import */
  imports: Array<ast.ImportNode>;
};

const isSuccessStatusCode = (statusCode: ast.StatusCode): boolean => {
  const code = Number(statusCode);
  return code >= 200 && code < 300;
};

/**
 * 成功レスポンスのデータ型を解決する。
 * `$ref` なら参照先のスキーマ型（例: `Book`）を直接使い、inline スキーマなら
 * plugin-ts が operation ファイルに書き出す `<Op>Status<code>` を使う。
 */
const resolveSuccessType = (params: {
  node: ast.HttpOperationNode;
  tsResolver: ResolverTs;
  typesFile: ast.FileNode;
  root: string;
  output: Output;
  group: Group | undefined;
}): SuccessType => {
  const { node, tsResolver, typesFile, root, output, group } = params;

  const members = node.responses
    .filter((response) => isSuccessStatusCode(response.statusCode))
    .map((response): SuccessType => {
      const schema = response.content?.[0]?.schema;
      const refName = ast.resolveRefName(schema);
      if (schema && refName) {
        return {
          expression: tsResolver.name(refName),
          imports: tsResolver.imports({ node: schema, root, output, group }),
        };
      }
      const name = tsResolver.response.status(node, response.statusCode);
      return {
        expression: name,
        imports: [
          ast.factory.createImport({ name: [name], path: typesFile.path }),
        ],
      };
    });

  if (members.length === 0) {
    return { expression: "never", imports: [] };
  }
  return {
    expression: [...new Set(members.map((m) => m.expression))].join(" | "),
    imports: members.flatMap((m) => m.imports),
  };
};

/** OpenAPI に書かれている status の一覧。`default` は数値にできないので含めない */
const resolveDocumentedStatuses = (
  node: ast.HttpOperationNode,
): Array<number> =>
  node.responses
    .map((response) => Number(response.statusCode))
    .filter((status) => Number.isInteger(status));

/** 必須の入力が何も無ければ options 引数を省略可能にする */
const isOptionsOptional = (node: ast.HttpOperationNode): boolean => {
  const hasRequiredParameter = node.parameters.some(
    (parameter) => parameter.required && parameter.in !== "cookie",
  );
  const hasBody = Boolean(node.requestBody?.content?.[0]?.schema);
  return !hasRequiredParameter && !hasBody;
};

const renderJsDoc = (node: ast.HttpOperationNode): string => {
  const lines = [
    node.description && `@description ${node.description}`,
    node.summary && `@summary ${node.summary}`,
    node.deprecated && "@deprecated",
    `{@link ${Url.toPath(node.path)}}`,
  ].filter((line): line is string => Boolean(line));
  return `/**\n${lines.map((line) => ` * ${line}`).join("\n")}\n */\n`;
};

const renderOperationFunction = (params: {
  node: ast.HttpOperationNode;
  names: OperationNames;
  success: SuccessType;
}): string => {
  const { node, names, success } = params;
  const optionsDefault = isOptionsOptional(node) ? " = {}" : "";
  const documented = resolveDocumentedStatuses(node).join(", ");

  return `${renderJsDoc(node)}export function ${names.fn}(
  options: Options<${names.options}>${optionsDefault},
): ResultAsync<${success.expression}, ${names.error}> {
  const { client: request = client, ...config } = options;

  return toResultAsync<${names.responses}>(
    request({
      ...config,
      method: "${node.method}",
      url: "${node.path}",
      throwOnError: false,
    }),
    [${documented}],
  );
}
`;
};

const operationFileEntry = (node: ast.HttpOperationNode) => ({
  name: node.operationId,
  extname: ".ts" as const,
  tag: node.tags[0] ?? "default",
  path: node.path,
});

const clientGenerator = defineGenerator<PluginFetchNeverthrow>({
  name: "fetch-neverthrow",
  operation(node, ctx) {
    if (!ast.isHttpOperationNode(node)) return null;

    const pluginTs = ctx.getPlugin(pluginTsName);
    if (!pluginTs?.options?.output) {
      ctx.warn(
        "Skipped: `pluginTs()` を plugins に追加してください。operation の Options / Responses 型を plugin-ts の生成物から import します。",
      );
      return null;
    }
    if (!ctx.getPlugin(pluginFetchName)) {
      ctx.warn(
        "Skipped: `pluginFetch()` を plugins に追加してください。生成物は plugin-fetch の `.kubb/client.ts` を呼び出します。",
      );
      return null;
    }

    const { root, resolver, config } = ctx;
    const { output } = ctx.options;
    const tsResolver = ctx.getResolver(pluginTsName);
    const tsOutput = pluginTs.options.output;
    const tsGroup = pluginTs.options.group ?? undefined;
    const runtime = resolveRuntimePaths(root);

    const file = resolver.file({ ...operationFileEntry(node), root, output });
    const typesFile = tsResolver.file({
      ...operationFileEntry(node),
      root,
      output: tsOutput,
      group: tsGroup,
    });

    const names: OperationNames = {
      fn: resolver.name(node.operationId),
      options: tsResolver.response.options(node),
      responses: tsResolver.response.responses(node),
      // 型名なので plugin-ts の命名規則（PascalCase）に合わせる
      error: tsResolver.name(`${node.operationId} Error`),
    };
    const success = resolveSuccessType({
      node,
      tsResolver,
      typesFile,
      root,
      output: tsOutput,
      group: tsGroup,
    });

    const bannerContext = {
      output,
      config,
      file: { path: file.path, baseName: file.baseName },
    };

    return [
      ast.factory.createFile({
        baseName: file.baseName,
        path: file.path,
        meta: file.meta,
        banner: resolver.default.banner(ctx.meta, bannerContext),
        footer: resolver.default.footer(ctx.meta, bannerContext),
        imports: [
          ast.factory.createImport({
            name: ["ResultAsync"],
            path: "neverthrow",
            isTypeOnly: true,
          }),
          ast.factory.createImport({
            name: ["client"],
            path: runtime.client,
            root: file.path,
          }),
          ast.factory.createImport({
            name: ["toResultAsync"],
            path: runtime.neverthrow,
            root: file.path,
          }),
          ast.factory.createImport({
            name: ["Options", "RequestError"],
            path: runtime.neverthrow,
            root: file.path,
            isTypeOnly: true,
          }),
          ast.factory.createImport({
            name: [names.options, names.responses],
            path: typesFile.path,
            root: file.path,
            isTypeOnly: true,
          }),
          ...success.imports.map((imp) =>
            ast.factory.createImport({
              name: imp.name,
              path: imp.path,
              root: file.path,
              isTypeOnly: true,
            }),
          ),
        ],
        sources: [
          ast.factory.createSource({
            name: names.error,
            isTypeOnly: true,
            isExportable: true,
            isIndexable: true,
            nodes: [
              ast.factory.createText(
                `export type ${names.error} = RequestError<${names.responses}>;\n`,
              ),
            ],
          }),
          ast.factory.createSource({
            name: names.fn,
            isExportable: true,
            isIndexable: true,
            nodes: [
              ast.factory.createText(
                renderOperationFunction({ node, names, success }),
              ),
            ],
          }),
        ],
      }),
    ];
  },
});

/**
 * `@kubb/plugin-fetch` の client を neverthrow の `ResultAsync` で包んだ関数を
 * operation ごとに生成する。型は `@kubb/plugin-ts`、HTTP 呼び出しは
 * `@kubb/plugin-fetch` の `.kubb/client.ts` に依存する。
 */
export const pluginFetchNeverthrow = definePlugin<PluginFetchNeverthrow>(
  (options) => {
    const { output = { path: "fetch-neverthrow", barrel: { type: "named" } } } =
      options;

    return {
      name: pluginFetchNeverthrowName,
      options,
      // 実行順のヒント。plugin-ts の型と plugin-fetch の client を参照する
      dependencies: [pluginTsName, pluginFetchName],
      hooks: {
        "kubb:plugin:setup"(ctx) {
          ctx.setOptions({ output });
          ctx.addGenerator(clientGenerator);

          const root = path.resolve(ctx.config.root, ctx.config.output.path);
          ctx.injectFile(createRuntimeFile(root));
        },
      },
    };
  },
);
```

### 呼び出し側を差し替える

無事に関数が生成され、 `generated/fetch-neverthrow` からimportして使用できるようになりました。「[どういうコードを生成させるか考える](#どういうコードを生成させるか考える)」で示した呼び出し側コードを、importだけ差し替えてそのまま使うことができます。

```diff ts:index.ts
- import { getBook } from "./getBook";
+ import { getBook } from "./generated/fetch-neverthrow";
```

#### Before & After

記事の冒頭、plugin-fetchの生成物をそのまま使っていたときの呼び出し側と並べてみます。

```ts:index.ts（Before）
import { getBook } from "./generated/clients";
import type { ApiError } from "./generated/types/ApiError";
import type { Book } from "./generated/types/Book";

try {
  const result = await getBook({
    path: { isbn: "4299039009" },
    throwOnError: false,
  });

  switch (result.status) {
    case 200:
      result.data satisfies Book; // 型が Book に絞られている
      break;
    case 404:
      result.error satisfies ApiError;
      break;
    default:
      result satisfies never;
  }
} catch (e) {
  console.error("transport error", e);
}
```

```ts:index.ts（After）
import { getBook } from "./generated/fetch-neverthrow";

const result = await getBook({ path: { isbn: "4299039009" } });

result.match(
  (book) => console.log("ok", book.title),
  (e) => {
    switch (e.kind) {
      case "http":
        console.error(e.status, e.body.message); // status は 404 に絞られる
        break;
      case "transport":
        console.error("transport", e.cause);
        break;
      case "unexpected":
        console.error("unexpected", e.status, e.body);
        break;
      default:
        e satisfies never;
    }
  },
);
```

呼び出し側から消えたものが3つあります。`try...catch` そのもの、`GetBookError` のような手書きのエラー型、`switch (res.status)` による振り分けです。代わりに、`GetBookError` はOpenAPIに書かれた `404` と `ApiError` に絞られ、想定外のステータスは `unexpected` として型に現れるようになりました。エンドポイントが増えたときは、OpenAPIスキーマを更新して `pnpm kubb generate` を実行すれば、同じ形の関数がその数だけ生成されます。

## 理想を追い求めし者へ

Kubbとneverthrowを組み合わせて、結果を `ResultAsync` で返すfetchクライアントを生成できるようになりました。自分のプロジェクトにちょうどいいfetchクライアントを探している人に向けて、この記事でやったことを振り返ります。

- plugin-fetchの生成物は便利だが、`throwOnError: false` でもネットワークエラーはthrowされるので、呼び出し側に `try...catch` が残る
- neverthrowで包めば `try...catch` は消えるが、エンドポイントごとに「エラー型の定義」「`ResultAsync` で包む処理」「レスポンスを `ok` / `err` に振り分ける処理」の3つを手で書くことになる
- 後ろの2つはどのエンドポイントでも手順が同じなので1つの関数に汎用化でき、エンドポイントごとに違うのはエラー型とステータスコードの一覧だけだった
- その差分を生成するKubbプラグインは、整理したコードを受け入れ条件にしてClaude Codeに任せた

結局、人間が考える必要があったのは「どういうコードを生成させたいか」を1つのファイルに手書きで整理するところまでで、そこから先はほとんど機械的な作業でした。手書きで整理する工程は自分の頭を整理するためのものでしたが、結果的にそのままエージェントへの指示と受け入れ条件になりました。

「理想のfetchクライアント」の形は人によって違うと思います。ただ、まず手で1つ書いてみて、変わる部分と変わらない部分を分ける、という手順は同じように使えるはずです。

### 旅はまだまだ続く？

今回の記事では扱いませんでしたが、OpenAPIの `default` レスポンスへの対応や、複数のContent-Typeを扱うAPIへの対応など、考える余地が残っています。理想を追い求める旅はまだまだ続きそうです。
